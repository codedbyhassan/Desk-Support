## 🎯 How It Works

### Traditional WebSocket Approach (❌ Current)
```
Browser A ─┐
           ├─→ WebSocket Server ←─ Browser B
           │     (on port 4000)
           └─→ Signaling messages
```
**Problems:**
- Need to manage separate server
- Scalability issues
- Connection management complexity
- No persistence

### New Supabase Realtime Approach (✅ Recommended)
```
Browser A ─┐
           ├─→ Supabase PostgreSQL ←─ Browser B
           │     (Realtime channel)
           └─→ Signaling messages stored in DB
                (automatic persistence & recovery)
```
**Benefits:**
- ✅ No separate server to manage
- ✅ Built-in persistence
- ✅ Automatic reconnection
- ✅ Better scalability
- ✅ Full audit trail
- ✅ Easy monitoring/debugging

### Step 3: Implement Supabase Signaling Client
(Replace current `src/services/video/signaling.ts`)

```typescript
import { supabase } from '@/lib/supabase'

export class SupabaseSignalingClient {
  private callId: string
  private peerId: string
  private handlers: ((msg: any) => void)[] = []
  private subscription: any

  constructor(callId: string, peerId: string) {
    this.callId = callId
    this.peerId = peerId
  }

  connect(): Promise<void> {
    return new Promise((resolve) => {
      // Subscribe to incoming signaling messages
      this.subscription = supabase
        .channel(`call:${this.callId}`)
        .on(
          'postgres_changes',
          {
            event: 'INSERT',
            schema: 'public',
            table: 'signaling_messages',
            filter: `to_peer_id=eq.${this.peerId}`,
          },
          (payload) => {
            const msg = payload.new
            this.handlers.forEach(h => h(msg))
          }
        )
        .subscribe(() => resolve())
    })
  }

  async send(message: any) {
    await supabase
      .from('signaling_messages')
      .insert({
        call_id: this.callId,
        from_peer_id: this.peerId,
        to_peer_id: message.to,
        message_type: message.type,
        payload: message.payload,
      })
  }

  onMessage(fn: (msg: any) => void) {
    this.handlers.push(fn)
  }

  close() {
    this.subscription?.unsubscribe()
  }
}
```

## 📊 Database Schema Overview

### Core Tables & Relationships
```
Companies
    ├── Video Calls (team_id, initiated_by, company_id)
    │   ├── Call Participants (user_id, peer_id)
    │   │   ├── Signaling Messages (from/to peer_id, payload)
    │   │   ├── Call Activity Logs (action, details)
    │   │   └── Call Statistics (metrics)
    │   └── Call Recordings (storage_path, status)
    └── Teams
        └── Team Members
```

### Key Columns

| Table | Column | Purpose |
|-------|--------|---------|
| video_calls | room_name | Unique call identifier |
| video_calls | status | pending → active → ended |
| video_calls | mode | video, lecture, or audio |
| call_participants | peer_id | WebRTC connection ID |
| call_participants | left_at | When user left (NULL if still in) |
| signaling_messages | payload | SDP or ICE candidate JSON |
| signaling_messages | expires_at | Auto-cleanup after 1 hour |

## 🔐 Security (RLS Policies)

All access is controlled by Row Level Security:

✅ **video_calls**: Only team members can view/create calls  
✅ **call_participants**: Users only see participants in their calls  
✅ **signaling_messages**: Only active participants can exchange  
✅ **call_recordings**: Company-scoped access  
✅ **call_activity_logs**: Can only view own call logs  
✅ **call_statistics**: Own stats or admin access
